# Quickreads admin

The admin remains at `/quickreads`, protected by the existing `quickreads-admin` session guard. The mobile and desktop interface uses local CSS, JavaScript and SVG icons; it has no CDN, jQuery, DataTables, chart-library or asset-build dependency.

Typography uses a 16px body size, 14px secondary text, 13px compact labels and headings of at least 16px, including on mobile. Sizes use rem units to respect browser font preferences. Explore covers are 60 × 88px (76 × 110px for the featured story), and library-picker thumbnails are 32 × 46px. The preview adapts its columns to keep story titles readable.

## Pages and workflows

- **Dashboard:** Saved stories, Reading, Finished and Apple-reader totals lead the overview, followed by catalogue counts, six latest saved records from all app versions, six latest app-reported reader/story states, 30-day account growth, newest readers with sign-in badges, library checks and six recent stories. Account counts, Apple membership and activity are queried on every refresh; catalogue/quality totals alone cache for five minutes and are invalidated by admin edits. Saved stories counts `user_purchase_records` from all app versions, including v2 favorites, without a date or reporting-retention limit. Reading/Finished count app-reported reader/story pairs, including guest installations, within the reporting retention window. Saved totals and six latest saves are queried fresh on every dashboard request.
- **Statistics:** 7/30/90/365-day presets or historical custom windows of up to 366 days, grouped by day or month. Missing buckets are filled with zero. Each report uses eight SQL queries on a cache miss, at most 366 chart points, and ten entries per ranking. Reports cache for five minutes and are invalidated by admin changes. Dates use the application timezone.
- **Story activity:** available directly in the sidebar, dashboard and Statistics. Shows current app-reported Saved/Reading/Finished counts, the latest applied state update, and 25 reader/story reports per page. Latest reports include registered reader names with links to their protected profiles; guests stay anonymous. Reading and saved states have separate observation timestamps, plus the server's received time. Search by story, author or registered reader; filter Saved/Reading/Finished/Not started, guest/account, Apple/other account and a specific reader ID. Visible removable filter chips expose story/reader restrictions as well as selected states. Metric cards preserve the reader/search filters and select a state. **By story** switches to paginated totals grouped separately for guests and accounts; selecting a story opens its latest reader reports. All times convert stored UTC to the application timezone. The report is private/no-store and uncached: **Refresh report** immediately reads committed activity.
- **Readers:** search full name/email, filter by Apple/other sign-in, have/no saved stories, and reported Reading/Finished/Saved/Not started/no-current-report state, sort and paginate. The primary Saved stories count links to the reader’s saved list and uses `user_purchase_records`; it includes older apps and v2 favorites. App-report links are secondary and explicitly labeled. Each row also shows reading/completion state totals and the latest applied update; accounts with no reports show No app reports yet. Apple membership is based on verified `apple_identities` records, including revoked identities; it is never inferred from a relay email or password. Empty names use **Reader #ID**. Profiles show authorization status/time, relay-address labeling, and saved-story counts and paginated lists first. A separate New app reports section shows current state totals and the ten latest reported story states; **All story reports** opens the full paginated report for that account. Saved-story lists retain old, null-date and duplicate records as before; ratings/comments each stop at ten. IDs identify profiles because legacy slugs are not unique. All reader views are private/no-store and read fresh data.
- **Explore:** a compact app-style preview with small covers and an adjacent section editor. Add, rename, remove and drag sections into order; arrow keys on section handles also work. **Add a section** opens a form for its name and hand-picked stories; cancelling leaves the layout unchanged. Every editable shelf has a story picker with selected stories, remove buttons, title/author search and alphabetical browsing. **Load more stories** browses the entire available library, 20 records at a time, without fetching bodies or counting the full catalogue. Story order shuffles daily at midnight UTC, including hand-picked shelves; the preview shows the same order as the app. Editing the membership of an existing automatic shelf preserves its current stories and switches it to hand-picked, retaining the section ID. Optional automatic selection rules are in a collapsed settings panel. Today’s pick stays first with one story; automatic Latest additions (Just added) remains the newest ten in creation-date/descending-ID order. Up to 20 sections and 24 stories per shelf keep responses bounded. Section movement buttons provide an alternative to dragging; section/preview-card removals offer Undo.
- **Stories:** search title/author, filter by author/category/classic/data issue, sort, and paginate. Editors search author/category lookups instead of downloading every record. Admin saves always set the cost to Free. Reading time is estimated at 200 words per minute when the editor loads and as story text changes, rounded to tenths of a minute. Cover uploads validate MIME/size and show a preview; the legacy `.jpeg` URL is preserved even when uploaded bytes are PNG/WebP, matching the existing app contract.
- **Authors/categories:** searchable lists, story counts, links to filtered stories, and focused forms. Category order respects the existing signed tiny-integer column (-128 to 127).

Latest additions is a system collection, not an editable category. It is excluded from category lists, dashboard category totals, story assignment lookups and the v2 category directory. Creating a category with this reserved name or assigning stories to its existing ID is rejected. Stories previously assigned there retain their data and visibility; choose a regular category when editing them. The existing category row/ID stays internally for older app versions and is protected from renaming/deletion through admin.

The legacy `/quickreads/app/categories` response retains that ID and reports the automatic collection's size. `/quickreads/app/categories/show?category_id=<existing ID>` returns the ten newest stories across categories, ordered by creation date and then descending story ID. A fresh catalogue with no legacy row receives a virtual category with ID `0`, without a database write. `/quickreads/app/stories/latest` exposes the same flat story list directly. These routes work independently of whether Explore includes a Latest additions shelf. Fewer than ten available stories returns the available set; an empty catalogue returns an empty list. No migration is needed for this system collection behavior.

Explore edits stay private until **Save Explore**. Previews resolve the current library without database writes. Saving stores the layout with a revision check so another open editor cannot silently overwrite it. Both `/quickreads/app/explore` and `/api/v2/explore` use this layout, preserving their respective response fields. Legacy Explore remains an array of `{title, collection}` objects with the featured item first; it defaults to six sections and supports a different count after curation. V2 includes stable section IDs and paged summaries. The shared resolver selects each shelf using its saved rules, then orders its stories deterministically by UTC date, section ID and story ID. The order stays stable during the day and reshuffles on the next day's requests without a cron job, migration or layout write. The `latest` source is exempt and always stays newest first, regardless of its heading. Admin initial previews, draft previews, saves, both public Explore APIs and v2 section pagination use this resolver. Story text and biographies are omitted from admin searches; all preview/API shelves are bounded and metadata is fetched in a batch. The old legacy Explore cache is ignored, so saved curation takes effect on the next request. V2 clients may retain responses for their existing 60-second HTTP cache lifetime. Continue reading remains local to the app, and its typography/spacing remain controlled by the client.

Lists return 25, 50 or 100 rows with preserved filters; story lists omit story text and author lists omit biographies. Editors keep slugs stable when titles/names change so existing links and artwork paths remain valid. Creation checks for slug collisions.

The old `/stories|authors|categories/edit` and `/delete` selection URLs redirect to the corresponding list. Their unused templates and the obsolete statistics controller were removed. Legacy application API routes and response contracts remain covered by regression tests.

Deletion requires an explicit checkbox. Authors/categories with stories cannot be deleted; first reassign their stories. Story deletion cleans up saved records, ratings, comments and local cover files. User deletion cleans up saved records, ratings, comments, v2 access tokens and password resets. These are permanent operations, as before; there is no soft-delete schema.

“Saves” means rows in `user_purchase_records`, not verified downloads or completed reads. Legacy duplicates count as separate saves. Distinct reader/story metrics exclude deleted entities. Null-date saves do not belong to a reporting window. A partially elapsed reporting day/month is included through today; no data after the selected end date is included.

Story activity uses the separate v2 `story_activity` reports. Each row is the latest known state for one reader and story, rather than an event log or lifetime action counter. Finished replaces Reading for that pair; Saved remains independent. Summary cards count reader/story pairs and follow the search/reader/story criteria; selecting a status filters the table without hiding the other summary totals. An unknown reading/saved state is shown as **Not reported**. Inactive reports expire after the configured retention window (90 days by default). State update times advance only when a report applies; duplicates/stale reports can be acknowledged without moving the time. Guest counts represent installations, not authenticated people. Guest reporting UUIDs/hashes, account emails, credentials and story bodies are never fetched or rendered by this report.

### Test activity from the iOS app

1. Deploy the updated PHP, Blade views and admin CSS; clear compiled views. This admin update adds no migration or API schema change. The existing `2026_10_15_000002_create_story_activity_tables.php` migration must already be applied to the Quickreads connection.
2. Open the dashboard and select **Refresh overview**. Open **Story activity**, select **Clear filters**, and check **Latest state update**. Active filter chips make any reader/story/status restriction visible.
3. In an iOS build with the `POST /api/v2/story-activity` transport enabled, open a story for reading. Select **Refresh report** in the admin: its latest row should show Reading and its report time.
4. Sign in and save that story. Refresh: Saved should appear independently of the reading state. Mark it finished through the app's completion flow and refresh: Finished replaces Reading, while Saved remains set. Remove the save and refresh: Not saved appears, with the reading state retained according to the app's reported state.
5. Sign up through Apple in the current app. Open **Readers → Apple** and confirm the account appears once, including after a returning sign-in. Open its profile and confirm its Apple authorization, optional private relay address and reported stories. Missing names should display Reader #ID.
6. Try guest reading and completion separately. Those rows appear as Guest reader and must not be reassigned to an account after login.

If the page is empty or the applied state update time does not change, confirm that the installed iOS build actually sends and receives successful acknowledgements from the activity endpoint. Existing legacy save/favorite calls alone do not report Reading or Finished. Offline queues may arrive after reconnecting/foregrounding. No fake production reports or backfill are created by opening this admin page. The app remains responsible for recording only successful actions and preserving Finished on reopening.

### Saved stories and app-reported saved state

Both the old save endpoints and the v2 favorites API write to `user_purchase_records`. Those rows remain the primary Saved stories counts and lists on the dashboard and reader pages. They have no activity-reporting retention cutoff and do not require `story_activity` rows. Counts preserve the existing save-record semantics, including old duplicates. Null-date records remain visible. The dashboard shows the latest six saved records; profiles paginate all saved records.

`story_activity.saved` is a separate report from the updated app. It is explicitly labeled App-reported saves and never replaces, deletes, backfills, or gets added to the saved-story records. No report is not evidence that a reader has no saved stories. Reports may expire independently. Reading and Finished continue to come only from reports, without guessing them from a save.

## Query bounds and account recording

The reader directory performs five metadata queries for a nonempty page: count, paginated rows (with indexed provider/saved-record subqueries), one grouped activity query restricted to visible account IDs, and two global account totals. The number of queries does not grow with page size. Profiles use at most ten queries, show at most ten current stories and preserve pagination for saved stories from all app versions. Shared activity scopes keep dashboard, directory, profiles and the full report consistent about retention and state ordering. No provider subjects, refresh tokens, access tokens or passwords are selected by these queries; activity views also omit email, guest reporting identifiers and story bodies.

Verified Apple signup already commits a canonical `users` row and its Apple identity together. Admin GET requests only read those records; returning sign-in does not create another reader, revoked authorization does not erase an account, and deleting the account removes it through the existing deletion flow. Existing signup/provider lifecycle protections and public API contracts are unchanged.

The October 18 admin update needs no new migration, environment setting or asset build. Deploy its PHP, views and admin CSS, then clear compiled views. Existing Apple/activity migrations must already be installed on the Quickreads connection.

## Deployment

Deploy the PHP/views, `public/css/quickreads-admin.css`, `public/js/quickreads-admin.js`, `public/css/quickreads-explore.css` and `public/js/quickreads-explore.js`. No npm build is required. Ensure previous Quickreads migrations, including `api_v2_tokens`, are already installed.

Run the additive migrations against the **Quickreads connection**:

```sh
php artisan migrate --database=quickreads --path=database/migrations/quickreads/2026_10_12_000001_add_admin_query_indexes.php --force
php artisan migrate --database=quickreads --path=database/migrations/quickreads/2026_10_12_000002_create_explore_layouts_table.php --force
php artisan view:clear
```

Rebuild the deployment's usual route/view caches if used. The existing public storage link and a writable public disk are required for covers.

The migration adds date, relationship, slug and per-user activity indexes. It does not delete or rewrite data. Index creation can take time and consume disk space on a large production database; schedule it with normal database-change procedures. `down()` removes only indexes introduced here. The new code functions before indexes are installed, but the performance improvement depends on them.

The Explore migration creates only `explore_layouts`; it does not rewrite stories or categories. Install it before serving the new editor/API code. An empty layout table uses the default sections until the first admin save. Dropping this table discards curation, so retain it when rolling back code.

## Verification

```sh
php vendor/bin/phpunit tests/Feature/Quickreads
node --check public/js/quickreads-admin.js
node --check public/js/quickreads-explore.js
php artisan view:cache
php artisan view:clear
```

The feature suite covers authentication, all admin pages, legacy redirects/API contracts, report bounds and caching, orphaned/empty data, pagination and filters, validation, cover storage, stable URLs and deletion cleanup. Explore checks cover private previews, save conflicts, daily order stability and UTC rollover, the chronological Just added exception, all automatic sources, validation limits, both API envelopes, custom section pagination and guest/favorite isolation. Tests replace every named database connection with isolated databases; never run a fresh migration against production to test this change.

The same suite was also run against an isolated MySQL 8.4 instance. A local synthetic benchmark with 250,000 saves spread across 730 days produced a cold 30-day report in approximately 41 ms with eight SQL queries and 10,290 in-range saves. This measures a local fixture, not production latency; a longer range necessarily reads more index entries. MySQL rankings aggregate the date window before joining story/user metadata to avoid scanning complete histories.

Desktop (1440px) and mobile (390px) browser checks use synthetic data and exercise login, report filters, asynchronous lookups, story updates, reader search/detail, navigation and responsive layouts. Explore checks also cover creating/cancelling named sections, paged story browsing, search, membership edits, drag ordering and save/reload persistence. No production data or admin accounts were changed during development.
